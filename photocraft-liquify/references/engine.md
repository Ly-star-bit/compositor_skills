# 引擎实测规律和高级写法（photocraft-liquify）

[SKILL.md](../SKILL.md) 的展开版：脚本内部怎么把"描好的边"变成 PhotoCraft 液化滤镜的笔触，为什么这样做，以及配方覆盖不了时怎么手写笔触。数字都是在 photocraft-cli 0.19.0 上量出来的，量法是让笔触作用在一张"每个像素存着自己坐标"的 16 位图上，再读回每个像素从哪来。

## 怎么和 PhotoCraft 说话

- `scripts/photocraft_mcp.py` 启动 `photocraft-cli mcp --automation-read-root <临时文件夹> --automation-write-root <临时文件夹>`，按 MCP 协议在标准输入输出上收发 JSON-RPC（`initialize` → `tools/call`）。只有引擎，没有窗口。
- 用到的 MCP 工具：`doc_open`、`doc_inspect`、`command_run`、`doc_save`、`doc_close`。引擎命令经 `command_run` 调用：`layer.selectTop`、`layer.stampVisible`、`layer.smartObjects.convertToSmartObject`、`filter.liquify`、`layer.setProps`、`layer.newAdjustmentLayer.*`、`image.adjustments.*`。
- 成品文档的搭法：打开照片（或分层文档的副本）→ 选中最上面一层 → `layer.stampVisible` 把可见画面盖印成新的一层 → 转成智能对象 → `filter.liquify` 作为它的智能滤镜 → 上面加色调调整层。下面的图层一概不动。照片只有一层时，盖印出来的就是它的副本（相当于 Ctrl+J）。输入是 `.pcraft` / `.psd` 时，网格图、量色、检查图用的都是引擎渲染出的可见画面（`doc_open` 后 `doc_save` 成 PNG）。
- 引擎只能读写那个临时文件夹：照片先复制进去，成品做好再移到照片旁边。出错时照片旁边什么都不会变。
- 和引擎的管道固定用 UTF-8，脚本自己的输出也固定用 UTF-8。交给系统默认编码的话，中文 Windows（GBK）在引擎第一次回传中文图层名或文件名时就解码失败：读回复的线程死掉，主线程一直等（在别人的 Windows 上实际出现过，用 GBK 区域设置能复现，`tests/run.sh encoding` 测的就是它）。图片读写不用 OpenCV 自己的 `imread` / `imwrite`（Windows 上只认系统编码的路径），统一走 `imdecode` / `imencode`。
- 环境变量 `PHOTOCRAFT_CONTROL_*` 会被去掉：这个技能从不连接正在运行的 PhotoCraft 程序。用户在 PhotoCraft 里开着同名 `.pcraft` 时，重跑之后要他自己关掉重开（或文件 › 恢复）。

## 液化笔触的规律

`filter.liquify` 的参数是 `{"strokes": [...], "layer": id}`，一次调用里的笔触依次作用在同一个位移场上，画面只重采样一次。

**前推（forwardWarp）**
- 压力 100 时，画笔中心下的内容完全跟着拖动走：拖 60 像素就移动 60 像素。压力按比例缩放（压力 50 移动一半），可以是小数。
- 影响半径 = 画笔直径的一半。密度 50 时，离中心 t 个半径处的移动量 ≈ (1 − t²)^1.5。
- **拖动按画笔直径的 2.5% 分步，不足一步的余量被丢掉。** 直径 640 的画笔一步是 16 像素，拖 14 像素等于没拖。所以脚本的每一笔都拖"整数步（至少两步）"，真正的移动量由压力承担。
- 沿轮廓每隔四分之一半径放一笔，相邻笔触叠加，总和约是单笔的 4.69 倍；单笔的量 = 目标量 ÷ 4.69。
- 不同直径的两串笔触在交界处叠加，初算一定不准。所以脚本**对着实测位移场校正**：跑一遍，量每个控制点实际移动了多少，按"想要 ÷ 实际"的 0.7 次方修正该点的量（带阻尼：相邻的点互相影响，不加阻尼会来回摆，实测第 3 轮比第 1 轮还差 8 像素），重复五轮（在缩小的坐标图上做，快），留下误差最小的那一轮，最后在原尺寸上验一遍，必要时再修一次。输出里的 `want>got` 就是这个结果。
- 靠近画面边缘的点只保留沿边缘方向的推力：朝着或背着边缘推，最外面几行像素会被拉花（实测"拉伸 50 倍"）。

**膨胀 / 收缩（bloat / pucker）**
- `points` 里每个点是一下。直径 300、速率 80 时，一下在半径一半处推开 2.4 像素，中心放大约 5%。
- 同一个点重复写几次就是点几下，效果累加；速率和压力都按比例缩放；`amount` 参数对它们无效。

**智能滤镜**
- 先 `layer.smartObjects.convertToSmartObject` 再 `filter.liquify`，液化就成了智能滤镜；导出的画面和直接滤镜逐像素一致（实测最大差 0）。成品 `.pcraft` 里的液化可以在 PhotoCraft 里关掉或重编。

**别的**
- `image.detectFaces` 的五个关键点在戴眼镜的脸上偏了 30–50 像素，不要用它定位，以网格图上读的坐标为准。
- 2100 万像素、约 100 笔：位移场几十毫秒，整个流程 4–5 秒。

## 力度从哪来

见 `scripts/pcraft_liquify.py` 开头的 `RECIPES`。四种配方：

| 种类 | 力度怎么分配 | 用它的部位 |
|---|---|---|
| profile | 按边上的位置（0 = 第一个点，1 = 最后一个点）查表 | jaw、cheek、neck、shoulder、hip |
| around | 以"离 `toward` 最近的点"为中心，按沿边的距离（单位：width）查表 | waist |
| limb | 均匀内收 `base`%，再加上"鼓出量超过 `slack`% 的部分"× `flatten`；鼓出量 = 点到"首尾两点连线"的距离 | upper_arm、forearm、thigh、calf、belly、back |
| joint | 一圈相同的 `inset`%，中间乘 `tip` | elbow、knee、wrist、ankle |

画笔直径 = max(配方的最小倍数 × width, 8.5 × 最大推动距离)。8.5 倍保证边缘两侧的压缩 / 拉伸不超过约 35%，皮肤纹理和背景不会糊。

limb 的"鼓出量"按每个点自己的内法线判断正负（点在首尾连线的外侧才算鼓出），不看 `toward` 落在连线的哪一侧：鼓得厉害的肢体，中轴线可能就在连线和边之间。总量在 `most` 处用 tanh 拐平，边描得长一点、短一点，不会推过验收过的最大值。

每个部位的量 = 配方 × `need` × 这个部位的 `strength` × `--strength`。`need` 是"这个人需要几成"：`clear` 1、`some` 0.5、`none` 0（脚本里的 `NEEDS`）。配方的数字是在一个人身上验收的，那个人的这些部位都明显需要修，所以配方是全量、是上限；别的人按 `need` 打折。任何部位不写 `need` 时脚本警告，并按 1 算（所以旧的计划结果不变）。计划里所有部位都是 `none` 又没有调色时，脚本什么都不写，以 `[SUCCESS] nothing to liquify` 结束。

为什么脸的 `need` 是让人看着判断，而不是像肢体那样从描的点里量出来：试过用"下颌那条边相对它首尾连线鼓出多少"来量。验收的那张脸鼓出脸宽的 7.9%，一张不需要修的瓜子脸约 4.7%，方向是对的；但这个数随"边从哪描到哪"变化很大，脸边被头发盖住时量到的是头发，而且只有两张脸可比。不够可靠，所以没有做成自动的。

安全限制：单条边最多移动 width 的 30%，也不能超过画面长边的 5%；`strength` 合计不超过 1.8。

## 高级写法：自己给像素数

配方覆盖不了的情况（手托着脸、只想动某一小段、要一个特殊方向）才用。和 `parts` 写在同一个 plan.json 里。

```json
{
  "contours": [
    {"name": "custom edge", "size": 300, "toward": [1500, 2000],
     "points": [[1200, 1900, 10], [1210, 1980, 16], [1230, 2060, 10]]},
    {"name": "explicit directions", "size": 240,
     "points": [[800, 900, 12, 1, 0], [805, 960, 12, 0.9, -0.4]]}
  ],
  "nudges": [{"name": "hand under jaw", "size": 560, "at": [1600, 2880], "toward": [1800, 2650], "px": 6}],
  "dabs": [{"name": "extra eye", "tool": "bloat", "size": 180, "at": [1617, 2463], "count": 1, "rate": 60}]
}
```

- `contours`：`size` 是画笔直径；每个点是 `[x, y, 像素数]`（方向由 `toward` 或整条的 `direction` 决定）或 `[x, y, 像素数, ux, uy]`（自己给方向）。像素数是这个点处边缘最终移动的距离，脚本同样会对着实测校正。
- `nudges`：一笔。把 `at` 周围直径 `size` 的一整块内容朝 `toward`（或 `direction`）挪 `px` 像素，中心挪得最多，边缘为零。适合"整只手连同脸颊一起挪一点"。
- `dabs`：膨胀 / 收缩，`count` 下，`rate` 是速率（1–100）。
- 这些不受配方的百分比限制，只受"不超过画面长边 5%"的限制，所以**自己负责不过头**：画笔直径至少是推动距离的 8 倍；关节和拐角用很小的数。

## 调色怎么算

`tone` 命令：
1. 取每个色块的中位数颜色，转 Lab。目标 = 参考图色块的 a、b（颜色）配上照片自己色块的 L（明暗）：只对齐颜色，不改明暗。环境（`surroundings`）只走 60%（`--surroundings` 可改），因为两张图里的环境通常不是同一种东西。
2. 主体色块（皮肤、嘴唇、白）的"照片 RGB → 目标 RGB"成为红、绿、蓝三条曲线要经过的点。曲线是**画出来的**（`pencil`，256 个输出值）：点与点之间的偏移量线性过渡、拐角抹圆，两端回到 (0,0) 和 (255,255)，斜率限制在 0.35–2.5 之间。不用"点曲线"是因为引擎会用样条穿过这些点，相邻的点靠得近、偏移方向又不同时，样条会在它们之间和之外甩出去，把没量过的色调（暗部、中性灰）染上颜色：实测过，弱一点的模型选的色块让整张图蒙了一层粉。这是「色调 · 肤色与白」曲线调整层。
3. 环境色块和主体的色相分得开（至少差 9°）时，再加一个「色调 · 环境」色相 / 饱和度调整层：范围只罩住环境的色相，起点离最近的肤色色相 4° 以外；色相偏移和饱和度是让引擎在一排色块上真算出来、逐个试出最接近目标的一组。分不开时不加这一层并说明。
4. 最后把定下来的各层在一排色块上真跑一遍，打印"照片 → 调色后 | 参考图"；同时跑三块中性灰（暗 / 中 / 亮），打印它们被带偏了多少，超过 12 就警告。

tone.json 就是一组调整层：`{"layers": [{"command": "layer.newAdjustmentLayer.curves", "name": "…", "params": {...}, "opacity": 1.0}, …]}`。可以手写任何 `layer.newAdjustmentLayer.*` 命令（参数格式见 `photocraft-cli commands --filter newAdjustmentLayer`），`apply --tone` 按顺序从下往上加。

## 测试

`probe` 命令：沿一行或一列取 13 像素宽的亮度（Lab 的 L），平滑后找前后 8 像素亮度差最大的几处，给读坐标的人一个数值上的对照。

`tests/run.sh`（只用命令行，没有窗口）：配方和计划解析、短笔触不被丢、校正后误差、画面边缘、字幕倾斜检查、调色拟合（画出来的曲线、中性灰不偏色）、成品和分层文档、各种拒绝覆盖的情况。测试照片是 compositor-retouch 的测试用的那张 NASA 标准照。
